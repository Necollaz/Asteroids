# Правила Написания C# Кода Для Unity-Проектов

## Общие Принципы

1. Один класс должен иметь одну понятную ответственность.
2. Если класс делает слишком много, раздели его на несколько маленьких классов.
3. `MonoBehaviour` используй только как мост между Unity и игровой логикой.
4. Чистую игровую логику пиши в обычных C# классах, а не в `MonoBehaviour`.
5. Не скрывай обязательные зависимости через `?.`.
6. Если обязательная зависимость не пришла, это ошибка настройки, ее нужно увидеть сразу.
7. Не смешивай разные способы создания зависимостей без причины.
8. Если используешь Zenject, зависимости лучше получать через DI, а не создавать через `new`.
9. Не используй `FindObjectOfType`, `GameObject.Find` и `Camera.main` в игровой логике.
10. Ссылки на объекты сцены передавай явно через `[SerializeField]` или Zenject.

## MonoBehaviour

1. Используй `MonoBehaviour` для методов Unity: `Awake`, `Start`, `Update`, `OnEnable`, `OnDisable`, `OnTriggerEnter2D`.
2. Держи `MonoBehaviour` классы тонкими.
3. `MonoBehaviour` может принимать input, коллизии, обновлять UI и хранить ссылки на объекты сцены.
4. `MonoBehaviour` должен передавать расчеты и решения обычным C# классам.
5. Методы жизненного цикла Unity делай `private`, если нет причины делать их публичными.
6. Не складывай всю игровую логику в `Update`.
7. Не создавай скрытые зависимости внутри `MonoBehaviour`.

## Зависимости И Zenject

1. Используй один понятный способ передачи зависимостей.
2. Если используешь Zenject, регистрируй зависимости в Installer.
3. Для обычных сервисов используй `Container.Bind<T>().AsSingle()`.
4. Для scene-компонентов используй `Container.Bind<T>().FromComponentInHierarchy().AsSingle()`.
5. Для классов с интерфейсами `IInitializable` или `IDisposable` используй `BindInterfacesAndSelfTo<T>()`.
6. Не используй `BindInterfacesAndSelfTo`, если у класса нет интерфейсов.
7. Не создавай через `new` классы, которые должны приходить через Zenject.
8. Если объекту нужны параметры при создании, используй factory.
9. Обязательные зависимости не должны быть nullable.
10. `Construct` или конструктор должны только сохранять зависимости, а не запускать игровую логику.
11. Классы с `ITickable`, `IFixedTickable`, `IInitializable`, `IDisposable` биндь через `BindInterfacesAndSelfTo<T>()`.
12. Не тикай сервисы вручную из `MonoBehaviour.Update` или `FixedUpdate`, если это можно сделать через `ITickable` или `IFixedTickable`.
13. Не используй `AsSingle` несколько раз для одного и того же concrete-типа.
14. Если нужен один instance под несколькими контрактами, используй один binding: `BindInterfacesAndSelfTo<T>().AsSingle()`.
15. Не добавляй обязательные компоненты через `AddComponent` в runtime молча.
16. Если prefab должен иметь компонент, проверяй его через `TryGetComponent` и кидай понятную ошибку, если компонента нет.
17. Factory должна создавать объекты с runtime-параметрами, а не скрывать зависимости внутри класса.
18. Не создавай сервисы, калькуляторы, селекторы, презентеры и контроллеры через `new` внутри gameplay-кода.

## Нейминг

1. Название класса должно ясно говорить, за что он отвечает.
2. Название метода должно описывать, что метод делает.
3. Не используй префикс `Try`, если метод не возвращает `bool`.
4. Используй `Show` и `Hide`, а не `TryShow` и `TryHide`, если метод ничего не возвращает.
5. Используй единственное число для одного объекта: `LoadingView`, а не `LoadingsView`.
6. Используй название по смыслу: `ScoreView`, а не `WalletView`, если UI показывает очки.
7. Избегай слишком общих названий вроде `Reset`, если можно назвать точнее.
8. Хорошие названия: `PrepareForFirstJump`, `SaveIfBetter`, `UpdateBestScore`.
9. Исправляй опечатки сразу: `gapCenterY`, а не `grapCenterY`.
10. Держи единый стиль названий во всем проекте.

## События

1. Для ключевых gameplay-событий используй Zenject `SignalBus`.
2. Обычные C# events используй только для локальных событий внутри View или маленького isolated-класса.
3. View может отдавать события вроде `PlayClicked`, `BuyClicked`, `SliderChanged`.
4. Gameplay-события вроде `OrderPickedUp`, `OrderCompleted`, `MoneyChanged`, `UpgradePurchased`, `PlayerHitByVehicle` должны быть SignalBus-сигналами.
5. UI, звук, реклама, сохранения и аналитика должны реагировать на сигналы, а не вызываться напрямую из gameplay-сервисов.
6. Сигналы объявляй отдельными маленькими классами с понятным названием: `OrderCompletedSignal`, `PlayerMoneyChangedSignal`.
7. Не передавай в сигнал лишние данные. Передавай только то, что реально нужно подписчикам.
8. Все сигналы регистрируй в Installer через `Container.DeclareSignal<TSignal>()`.
9. Подписки на SignalBus делай в `IInitializable.Initialize`, отписки в `IDisposable.Dispose`.
10. Не смешивай SignalBus и C# events для одного и того же глобального события.

## Игровое Состояние

1. Игровым потоком должен управлять один понятный класс или сервис.
2. UI не должен напрямую перезапускать сцену или менять состояние игры.
3. UI должен показывать данные и сообщать о нажатиях.
4. Управление паузой должно быть централизовано.
5. Не меняй `Time.timeScale` из разных несвязанных классов.
6. Создай `GamePauseService` или похожий сервис для `Pause` и `Resume`.
7. Старт, рестарт, поражение и возврат в меню должны быть отдельными понятными сценариями.
8. Не перезагружай сцену, если состояние можно аккуратно сбросить.
9. Сбрасывай только те системы, которые действительно нужно сбросить.
10. Отделяй логику меню от логики игрового процесса.

## Async И Обработка Ошибок
1. `async void` используй только в Unity lifecycle/event methods, где нельзя вернуть `Task`.
2. Каждый `async void` обязан иметь `try/catch`.
3. Если в async-методе временно выключаются кнопки или input, возвращай состояние в `finally`.
4. Не игнорируй результат инициализации async-сервисов.
5. Если bootstrap-инициализация провалилась, не продолжай загрузку следующей сцены молча.
6. Ошибка async-загрузки должна содержать понятный контекст: что грузили, какой id/address, какая сцена.
7. После Addressables `LoadAssetAsync` проверяй `handle.Status`.
8. Если Addressables handle невалидный, не обращайся к `Status`, сначала проверяй `handle.IsValid()`.
9. Не оставляй `_isLoading`, `_isInitialized`, `_isInteractable` в неверном состоянии после ошибки.
10. Для сложной async-логики выноси ее из View в отдельный service/flow-класс.

## UI

1. View-классы должны только отображать данные и отдавать события кнопок.
2. UI не должен содержать игровые правила.
3. UI не должен сам решать, что происходит в игре.
4. Кнопки должны вызывать события, а не выполнять игровую логику напрямую.
5. Текст в UI обновляй через методы View или подписку на события.
6. UI-ссылки храни через `[SerializeField]`.
7. Не храни повторяющиеся строки прямо в коде.
8. Панели показывай и скрывай через `Show` и `Hide`.
9. `DefeatMenuView`, `GameMenuView`, `LoadingView` не должны знать, как работает gameplay.
10. Для разных экранов делай отдельные View-классы.
11. Анимации успешного действия запускай только после успешной проверки результата.
12. Например, сначала `TryPurchase`, потом анимация кнопки покупки.
13. Если действие не удалось, UI должен показать недоступность, а не проигрывать success-анимацию.
14. Кнопки, которые запускают async-действие, должны блокироваться до завершения операции.
15. После ошибки кнопки должны возвращать интерактивность через `finally`.

## Движение И Физика

1. Логику движения отделяй от обработки Unity-событий.
2. Если движение усложняется, выноси его в отдельный класс.
3. Не меняй физику объекта из многих разных мест.
4. Используй один выбранный способ движения для объекта: `CharacterController`, `Rigidbody`, `NavMeshAgent` или ручное движение Transform.
5. Не смешивай разные способы движения одного объекта без явной причины.
6. Физические настройки храни через `[SerializeField]` или settings.
7. Не используй магические числа для `speed`, `gravity`, `acceleration`, `turnSpeed`, `drag`, `stamina`.
8. Если объект не должен вращаться, заморозь rotation.
9. Используй layers для фильтрации столкновений.
10. Логику реакции на столкновения отделяй от движения, если она растет.
11. Если объект двигается без физики, не добавляй ему `Rigidbody` без необходимости.
12. Для Android избегай большого количества динамических Rigidbody.
13. Реакцию на столкновения отделяй от движения в отдельный service/controller.

## Object Pool

1. Используй пул для часто создаваемых объектов.
2. Не используй `Instantiate` и `Destroy` постоянно во время игры.
3. По возможности заранее прогревай пул.
4. Возвращенный в пул объект должен быть выключен.
5. Взятый из пула объект должен быть включен только в нужный момент.
6. Добавь защиту от двойного `Release`.
7. Один и тот же объект не должен попасть в очередь пула дважды.
8. При рестарте возвращай активные объекты в пул.
9. Перед скрытием игрового root-объекта возвращай активные объекты в пул.
10. У каждого пула должна быть понятная зона ответственности.

## Настройки

1. Игровые параметры храни в `[SerializeField]`, settings-классах или `ScriptableObject`.
2. Если у класса слишком много `[SerializeField]`, вынеси их в отдельный settings-класс.
3. Для переиспользуемых настроек используй `ScriptableObject`.
4. Для простых настроек внутри одного класса можно использовать `[Serializable]` class.
5. Не разбрасывай одинаковые константы по разным классам.
6. Ключи сохранений храни в `const`.
7. Имена параметров анимации храни в `const`.
8. Значения вроде `InfiniteLoops = -1` лучше выносить в константы.
9. Дефолтные значения должны быть адекватными.
10. Проверяй обязательные ссылки через `OnValidate`, если это помогает.

## Производительность Для Android И WebGL

1. Избегай лишних аллокаций в `Update`.
2. Не используй LINQ в часто вызываемом gameplay-коде.
3. Не создавай и не уничтожай объекты постоянно во время игры.
4. Не вызывай `GetComponent` каждый кадр.
5. Кэшируй компоненты в `Awake`.
6. Не используй `Camera.main` в игровой логике.
7. Не создавай строки каждый кадр.
8. Используй object pool для препятствий и повторяющихся объектов.
9. UI обновляй по событиям, а не каждый кадр.
10. Проверяй производительность на целевой платформе, а не только в Unity Editor.
11. Не добавляй компоненты через `AddComponent` во время gameplay без необходимости.
12. Не создавай Addressables/Instantiate/Destroy в частых gameplay-сценариях без пула.
13. Сервисы, которые должны обновляться каждый кадр, лучше делать `ITickable`/`IFixedTickable`, а не вручную дергать из View.
14. Не делай `GetComponent` в циклах по множеству объектов каждый кадр.
15. Для повторяющейся логики видимости, расстояния, движения делай общий переиспользуемый класс.

## Assembly Definition

1. Используй asmdef, когда проект начинает расти.
2. Делай зависимости между assembly односторонними.
3. `Core` не должен зависеть от UI или конкретного gameplay-модуля.
4. Игровая логика по возможности не должна зависеть от UI.
5. Не держи весь большой проект в одном asmdef.
6. Делай assembly по модулям проекта: `Core`, `Application`, `Player`, `Orders`, `City`, `Economy`, `Upgrades`, `Audio`, `Settings`, `Saves`, `Ads`, `Rendering`, `Installers`.
7. Не создавай слишком много asmdef слишком рано.
8. Installer может знать о модулях, которые он связывает.
9. Общие утилиты выноси в `Core`.
10. Проверяй зависимости assembly при добавлении нового кода.
11. Runtime asmdef не должен ссылаться на Editor asmdef.
12. UI/View assembly не должна быть зависимостью Core-логики.
13. Если модуль использует DOTween, Addressables, AdMob или Zenject, явно добавь нужные asmdef references.
14. После переноса класса между модулями проверь asmdef-зависимости.

## Code Style

1. `private` поля называй через `_camelCase`.
2. Классы, методы, свойства и события называй через `PascalCase`.
3. Локальные переменные и параметры называй через `camelCase`.
4. Для постоянных значений используй `const`.
5. Для зависимостей, которые задаются один раз, используй `readonly`.
6. Методы должны быть короткими и понятными.
7. Удаляй неиспользуемые `using`.
8. Держи единое форматирование.
9. Не пиши комментарии, которые просто повторяют код.
10. Пиши комментарии только там, где нужно объяснить неочевидное решение.

## Структура Папок И Namespace

1. Namespace должен соответствовать папке, где лежит файл.
2. В папке `View` должны лежать только `MonoBehaviour` и маленькие `[Serializable]` view/reference-классы для Inspector.
3. Presenter-классы клади в `Presentation` или `Presenters`, а не в `View`.
4. Сервисы и чистую runtime-логику клади в `Runtime`, `Core`, `Flow`, `Services`, `Calculation`.
5. Factory-классы клади в `Factories`.
6. Object pool-классы клади в `Pooling`.
7. ScriptableObject, settings, enum и data-классы клади в `Data`, `Settings` или `Types`.
8. Editor-классы должны лежать только в папках `Editor`.
9. Не клади новый класс рядом с главным классом только потому, что он был создан во время его рефакторинга.
10. Если файл переносится между папками, проверь namespace и asmdef references.

## Валидация Prefab И Scene References

1. Обязательные scene-ссылки проверяй через `OnValidate`, если класс является `MonoBehaviour`.
2. Обязательные runtime-компоненты prefab проверяй явно через `TryGetComponent`.
3. Если обязательный компонент отсутствует, кидай понятную ошибку с именем prefab/object.
4. Не добавляй обязательные компоненты через `AddComponent` в runtime, если это ошибка настройки prefab.
5. Для проверки игрока не используй `CompareTag`, если логика критичная.
6. Вместо тега добавляй marker-компонент, например `PlayerMarker`, и проверяй через `TryGetComponent`.
7. Не полагайся на имя объекта в логике, если можно передать ссылку или компонент.
8. Collider-настройки, trigger-настройки и обязательные ParticleSystem лучше валидировать отдельным validator-классом.
9. Неправильная настройка сцены должна проявляться понятной ошибкой при запуске, а не тихим неработающим поведением.
10. Не скрывай ошибку настройки через `null` checks без сообщения.

## Данные И Коллекции
1. Не отдавай наружу изменяемые списки напрямую.
2. Если внешний код должен только читать коллекцию, возвращай `IReadOnlyList<T>`.
3. Если нужно полностью защитить данные, возвращай копию коллекции.
4. Изменение save-data должно происходить через методы самого save-класса.
5. Если поиск по списку происходит часто или по id, собери `Dictionary`.
6. Не делай линейный поиск в часто вызываемом коде, если данные можно подготовить заранее.
7. Конфиги должны валидировать дублирующиеся id.
8. Id настроек должны быть стабильными и не зависеть от display name.
9. Data-классы не должны знать про UI, Audio, Scene и MonoBehaviour.
10. Save-data должна быть простой, сериализуемой и без gameplay-логики.

## Addressables И Внешние SDK

1. Все Addressables-загрузки должны проверять `AsyncOperationStatus`.
2. При ошибке загрузки выбрасывай понятное исключение с address/id.
3. Храни и освобождай Addressables handles централизованно.
4. Не теряй handle после загрузки asset/prefab.
5. Не продолжай gameplay-flow, если обязательный asset не загрузился.
6. Внешние SDK инициализируй через отдельный initializer/service.
7. Результат инициализации SDK нельзя игнорировать.
8. Неиспользуемые SDK-сервисы удаляй или доделывай до рабочего состояния.
9. Если есть `RewardedAdService`, он должен реально показывать rewarded-рекламу или быть удален.
10. Тестовые id рекламы и production id должны храниться в config.

## Чеклист Перед Завершением Фичи

1. У каждого класса есть одна понятная ответственность?
2. Можно ли часть логики вынести из `MonoBehaviour` в обычный C# класс?
3. Все обязательные зависимости передаются явно?
4. Зависимости создаются единым способом?
5. Нет ли обязательных зависимостей, спрятанных за `?.`?
6. Нет ли магических строк или чисел?
7. UI отделен от игровой логики?
8. Игровое состояние меняется из понятного места?
9. Все подписки на события корректно отписываются?
10. Можно ли понять работу фичи без ручного поиска объектов по всей сцене?
11. Нет ли `async void` без `try/catch`?
12. Не игнорируется ли результат async-инициализации?
13. Глобальные gameplay-события сделаны через SignalBus?
14. Нет ли runtime `AddComponent` для обязательных компонентов prefab?
15. Не отдается ли наружу изменяемый `List<T>`?
16. Нет ли линейного поиска по id там, где нужен словарь?
17. Namespace соответствует папке?
18. View не содержит бизнес-логику?
19. Tick/FixedTick логика не дергается вручную из View, если можно использовать Zenject tickable?
20. Все ошибки настройки сцены/prefab будут понятны по сообщению в консоли?
